# 研究报告：MVE 托管期结束后的"墓碑交接"可行性

> 代号：IS13（OPEN，仅调查未编码）
> 证据来源：corelib 2.1.4 源码（GraveStone 1.21.1-1.0.40 的后端，GitHub henkelmax/corelib 1.21.1 分支）、
> refer/gravestone-1.21.1 源码、NeoForge 21.1.250 反编译源码。

## 一、问题

有服务器管理员希望：MVE 托管结束（超时/放弃）后，未保留物品**不要原地爆出**，而是被墓碑模组托管（生成墓碑）。
核心疑问：存在"死亡之后、墓碑之前"的时刻吗？MVE 托管期结束那一刻，是否无计可施？

## 二、时间线事实（源码核实）

```text
ServerPlayer.die()
 ├─ LivingDeathEvent 派发（HIGHEST→LOWEST）
 │    └─ corelib @LOWEST：deathMap[玩家] = Death.fromPlayer(玩家)
 │        （快照：完整物品栏/经验等级/位置/名字 —— 此时物品仍在背包里）
 ├─ 发送 ClientboundPlayerCombatKillPacket
 └─ dropAllDeathLoot()
      ├─ captureDrops 收集全部掉落（背包 dropAll + 装备）
      ├─ dropExperience
      └─ LivingDropsEvent 派发（HIGHEST→LOWEST）★ "死亡之后墓碑之前"的时刻就是这个派发窗口
           ├─ corelib @LOWEST：death = deathMap.remove(玩家)
           │    death.processDrops(掉落集合)   ← 按 ItemStack.equals 与死亡快照匹配槽位，
           │                                      匹配不上的进 additionalItems
           │    post PlayerDeathEvent
           │      └─ GraveStone：填墓碑方块实体 + storeDeath（讣告/恢复命令用）
           │         + removeDrops() → drops.clear()
           └─ 事件结束后：剩余 drops.forEach(addFreshEntity)  ← 唯一的实体入世点
```

结论：
1. **"死亡之后墓碑之前"的时刻存在**，就是 `LivingDropsEvent` 的派发窗口（同一调用栈内）。
2. 管线结束后**没有任何标准入口**能让墓碑再接管——墓碑类模组不监听物品实体生成，也没有"后期入库"API。
3. **隐藏问题**：corelib 与 MVE 的托管挂点同为 LOWEST 优先级，执行顺序取决于注册顺序（竞态）：
   - corelib 先跑 → 全部进墓碑 → MVE 看到空集合 → 静默退出（设计书已覆盖）；
   - MVE 先跑 → MVE 全部接管 → corelib 对空集合 `processDrops` → **死亡快照全部槽位被清空并依然生成一座空墓**（corelib/GraveStone 均不跳过空死亡），外加 MVE 选择流程照常。空墓是化妆品级问题但应处理。

## 三、可行策略（调查结论，未编码）

### 策略 A：结算时重放掉落事件（推荐，通用）

超时/放弃结算且玩家尚未重生时，MVE 把未保留物品构造成 `ItemEntity` 集合，调用
`CommonHooks.onLivingDrops(player, 死亡来源, drops, recentlyHit)` **重放一次掉落管线**：

- 该钩子就是死亡管线派发 `LivingDropsEvent` 的原装入口（public static，返回是否被取消）；
- corelib 再次命中：`deathMap` 未命中（死亡时已消费）→ 回退 `Death.fromPlayer(玩家)`；
  此刻玩家仍躺在死亡点、物品栏已被 MVE 清空、经验冻结为 0 → **全部未保留物品进 additionalItems，
  PlayerDeathEvent 触发，死亡点生成一座含全部未保留物品、经验 0 的新墓碑**，无经验双返还；
- 事件未被取消且集合有剩余 → MVE 照常 `addFreshEntity`（当前行为成为自然兜底）；
- 无任何模组接手时行为与现状完全一致——**零 per-mod 适配，符合"兼容而非适配"**。

适用窗口：超时结算（玩家仍处于死亡状态躺在原地）。
不适用：点"重生"触发的结算（玩家实体已在重生流程中，位置/状态语义错位——保持直接掉落）；
登出放弃（连接拆除期实体时序风险——保持直接掉落）。

### 策略 B：接管优先级配置化（`dropsPriority`）

- `LOWEST`（现状）：墓碑优先语义成立时 MVE 静默退出；需接受"同优先级竞态 + 空墓"问题；
- `HIGHEST`：MVE 先行托管（含取消 LivingDropsEvent 以压制空墓与讣告副作用），
  墓碑由策略 A 在结算时接管。
- 代价：HIGHEST 模式下"缺席→禁用"的 fate 判定退化（其他接管者尚未运行），消失诅咒需提前自检；
  Curios 的掉落规则（NORMAL）会被 MVE 抢先——其显式支持需要同步提前。

### 策略 C：文档化限制（最保守）

不提供"交给墓碑"，结算=原版掉落。墓碑服务器管理员如果不满，只能关掉 MVE 或墓碑之一。
不推荐——策略 A 的成本很低且完全通用。

## 四、待实测风险（策略 A 实施前需验证）

1. GraveStone 对"重放死亡"的副作用：讣告（giveObituaries 会往玩家背包塞讣告——玩家还死着，可行）、
   storeDeath 记录翻倍（一次真实死亡 + 一次重放 = DeathManager 两条记录）、墓碑位置搜索失败时的兜底
   （corelib 的 grave 定位失败 → removeDrops 不会被调用 → 集合剩余 → MVE 兜底掉落 ✓ 已从源码确认）。
2. 玩家经验冻结为 0 → 墓碑存 0 经验 → 无双返还 ✓（已从 Death.fromPlayer 确认读 experienceLevel）。
3. 重放事件的 `recentlyHit` 传 false、`source` 用死亡来源——各监听者的上下文假设需实测。
4. Corail Tombstone / You're in Grave Danger 未验证，但"LivingDropsEvent 集合摘除"是 1.21.1 生态标准契约
   （inventory-protection 同款），预期兼容。
5. 登出放弃路径的重放风险（实体拆除时序）——建议不支持，保持直接掉落。

## 五、建议

实施策略 A + B（B 作为配置项 `dropsPriority`，默认保持 LOWEST），策略 A 的重放仅覆盖
"玩家仍处死亡状态"的结算路径。实施顺序放在核心流程稳定之后，先行用 GraveStone 实测表（第四节）验证。
