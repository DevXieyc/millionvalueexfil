# Million Value Exfil（MVE）可行性分析与环境检测报告

> 生成日期：2026-09-29
> 分析方式：neoforge-dev MCP 工具 + 本地 Gradle 环境，全部结论基于 **1.21.1 / NeoForge 21.1.250 实际反编译源码**核对，非凭记忆推断。
> 源码核对所用归档：`build/moddev/artifacts/neoforge-21.1.250-sources.jar`（补丁后的 MC+NeoForge 源码）、`neoforge-21.1.250.jar`（NeoForge 二进制）、bus-8.0.5.jar（事件总线）、`refer/` 下 5 个参考模组源码包。

## 一、结论（TL;DR）

**MVE 在 1.21.1 / NeoForge 21.1.250 基线上技术可行，无硬性阻塞点。**

- 环境已就绪并通过今日复验构建（exit 0）。
- 死亡接管可以**纯事件驱动**实现（不需要服务端 Mixin）：`LivingDeathEvent`（记录/冻结）→ `LivingDropsEvent`（从掉落集合中取走物品）→ `LivingExperienceDropEvent`（拦截经验）→ `PlayerRespawnEvent`（返还）。
- 客户端死亡界面替换需要 **1 个客户端 Mixin**（`ClientPacketListener#handlePlayerCombatKill`），注入点已核对。
- 设计书中 2 处与实际 API 不符，需要按本报告修正（`PlayerDropsEvent` 在 NeoForge 1.21.1 中不存在；槽位 ID 表与 1.21.1 实际值不一致）。
- 与 5 个参考模组的兼容性均已从源码层面验证接管机制，全部存在明确的共存策略。

## 三、核心接管链路（源码核对）

以下是 MVE 依赖的完整死亡结算路径，**每一环都已在 21.1.250 源码中确认**：

```text
ServerPlayer.die(DamageSource)                    ServerPlayer.java:685
 ├─ CommonHooks.onLivingDeath(...)                → posts LivingDeathEvent（可取消）
 │    ★ MVE 挂点①：LOWEST 优先级（此时未被取消 ⇒ 死亡成立）
 │      记录 X0 / 槽位快照 / ItemStack 身份映射，发送"预备界面"载荷
 ├─ 发送 ClientboundPlayerCombatKillPacket（死亡消息，顺序在挂点①之后 ⇒ 客户端先收到 MVE 载荷）
 └─ dropAllDeathLoot(...)                         LivingEntity.java:1462
      ├─ captureDrops(new ArrayList<>())          ← NeoForge 补丁：收集全部掉落
      ├─ dropFromLootTable / dropCustomDeathLoot
      ├─ dropEquipment() → Player.dropEquipment   Player.java:693
      │    ├─ destroyVanishingCursedItems()       ← 消失诅咒物品在此被原版销毁
      │    └─ inventory.dropAll()                 ← 0–35 主背包 + 盔甲 + 副手全部生成 ItemEntity
      │       （ServerPlayer.drop 补丁：ServerPlayer.java:1903，captureDrops 非空时进入收集）
      ├─ dropExperience(...) → getExperienceReward
      │    ★ MVE 挂点③：LivingExperienceDropEvent（LOWEST，取消 ⇒ 经验球不生成）
      └─ drops = captureDrops(null)
         CommonHooks.onLivingDrops(...)           → posts LivingDropsEvent（可取消，携带可变集合）
          ★ MVE 挂点②：LOWEST 优先级（最后执行）
            从 event.getDrops() 中【移除】MVE 确认接管的 ItemEntity（不取消事件）
            集合中剩余的物品照常 addFreshEntity 生成（其他模组/原版语义不变）
```

关键事实（均带源码出处）：

1. **玩家掉落会流经 `LivingDropsEvent`。** NeoForge 给 `Entity` 增加了 `captureDrops` 机制（`Entity.java:3690-3707`），并在 `ServerPlayer#drop`（`ServerPlayer.java:1903`）与 `Entity#spawnAtLocation`（`Entity.java:1980`）中优先进入收集集合。因此 `inventory.dropAll()` 生成的背包/盔甲/副手物品**不会直接入世**，而是统一出现在 `LivingDropsEvent.getDrops()`（`LivingEntity.java:1463-1475`）。
2. **`LivingDropsEvent` 的集合是可变列表，事件不取消、只摘除自己的条目**，其余条目由事件尾部 `drops.forEach(e -> level().addFreshEntity(e))` 正常生成。这正好实现设计书"只取得能证明属于自己的物品，其余不干预"的兼容原则，也避免了"取消事件 = 全有全无"的粗粒度问题。
3. **`PlayerEvent.PlayerDropsEvent` 在 NeoForge 1.21.1 中已不存在**（对 `neoforge-21.1.250.jar` 做 class 搜索，`PlayerEvent` 的 20 个内部类中无 `PlayerDrops`）。旧 Forge 时代"监听 PlayerDropsEvent 拦截玩家掉落"的方案不可用，必须采用上表链路。（`LivingDropsEvent` 仍然存在。）
4. **事件优先级顺序**：bus 8.0.5 的 `ListenerList.buildCache()` 按 `EventPriority.values()` 顺序拼接监听器，即 **HIGHEST → HIGH → NORMAL → LOW → LOWEST 依次调用，LOWEST 最后执行**；且默认不接收已取消事件（`SubscribeEvent(receiveCanceled=false)`）。MVE 的三个挂点全部用 `LOWEST`，天然排在 GraveStone（NORMAL）、inventory-protection（NORMAL）等接管者之后，与"无法证明归属时不接管"的设计一致。
5. **消失诅咒物品在 `destroyVanishingCursedItems()` 中被原版销毁**（`Player.java:696`，发生在 `dropAll` 之前），到达 `LivingDropsEvent` 时已不存在。若要按设计书在 UI 中以"禁用状态"展示，需要在挂点①扫描并预摘除（见 §6.3）。

### 3.1 设计书触发条件与实际 API 对照

| 设计书条件 | 实际实现（已核对） |
| --- | --- |

## 四、逐项可行性

### 4.1 死亡事务与服务端权威

- **两阶段事务**：挂点①建立"候选事务"（记录 X0、槽位快照、`ItemStack` 身份映射 `IdentityHashMap<ItemStack, SlotRef>`）；挂点②提交正式事务（从 drops 集合摘除身份匹配的 ItemEntity）。若挂点①之后死亡被其他模组取消（`LivingDeathEvent.isCanceled()`，需 `receiveCanceled=true` 监听）或挂点②未触发（同一调用栈内必然触发，除非死亡被取消），候选事务当刻丢弃——**"濒死复活模组未阻止死亡时才介入"**由该机制天然保证。
- **身份匹配的可靠性**：`inventory.dropAll()` 把背包中**原 ItemStack 实例**直接传入 `player.drop` → `ItemEntity` 包装同一实例 → `ItemEntity.getItem()` 与快照身份一致。匹配失败的条目（被其他模组在中途替换/新增）留在集合中原样掉落，符合 fail-open 原则。
- **客户端只提交 `(事务ID, 版本号, 条目ID, 操作类型)`**：自定义 `CustomPacketPayload`（NeoForge `RegisterPayloadHandlersEvent`，文档 `docs/networking/payload.md`）。费用 C(n)、n_max、经验结算全部服务端重算。
- **幂等与崩溃恢复**：事务持久化为 `SavedData`（`net/minecraft/world/level/saveddata/SavedData`，文档 `docs/datastorage/saveddata.md`），键为玩家 UUID，内容含事务版本号、条目 UUID、剩余刻数。物品序列化用 `ItemStack.CODEC` + `registryAccess()`（参考模组 inventory-protection 即用 `stack.save(HolderLookup.Provider)` 的同款方案）。每次状态变更 `setDirty()`；关键转换（摘除物品、结算）后可立即强制存盘，把崩溃窗口缩到最小。
- **选择时间 T=20t**：`ServerTickEvent.Post`（`net/neoforged/neoforge/event/tick/ServerTickEvent$Post`，已确认存在）递减剩余刻数；服务器关闭期间无 tick，时间自然冻结，符合"关服不消耗、恢复后继续"。

### 4.2 经验冻结与结算

- **拦截经验球**：`LivingExperienceDropEvent`（已确认存在）`setCanceled(true)` ⇒ 原版死亡不掉经验球；玩家经验字段为 public（`Player.experienceLevel`，`Player.java:177`），配合 `giveExperiencePoints`（`Player.java:1718`）做快照与重设。inventory-protection 采用完全相同的"取消事件 + 重生时 `giveExperiencePoints`"组合，已验证可行。
- **费用曲线 C(n)=⌊1395·n(n+1)/1332⌋** 与反查等级用的分段函数 E(L) 均为纯数学（E(L) 即原版 0→L 级总经验曲线，与设计书一致；C(36)=1395=E(30) 自洽）。全部可配置化无技术障碍。
- **剩余经验掉落 D(Xᵣ)=min(7·Lᵣ,100)** 与原版死亡经验规则一致（`ServerPlayer#getExperienceReward` 同式），结算时 `ExperienceOrb.award(level, pos, amount)`（`ExperienceOrb.java:148`）生成，自动按原版 orb 容量拆分。

### 4.3 界面与同步

- **倒下玩家选择界面**：客户端 Mixin 注入 `ClientPacketListener#handlePlayerCombatKill`（`ClientPacketListener.java:1711`，方法体已核对：`setScreen(new DeathScreen(...))` 是唯一替换点）。服务端在挂点①（死亡事件内）先发"预备"载荷、之后才发送原版 combat kill 包——两者在同一连接队列中**顺序保证**，客户端标志位就绪后 Mixin 用 `MVEDeathScreen` 替换 `DeathScreen`。若事务未提交（挂点②空手而归），服务端发"放弃"载荷，客户端自行 `setScreen(new DeathScreen(msg, hardcore))` 回退到原版界面。
  - 界面本体为普通 `Screen` 子类：`GuiGraphics.renderItem` 渲染图标/耐久/数量/附魔光效，`renderTooltip` 出 Tooltip，经验条用原版精灵图绘制，滚动条自绘（鼠标滚轮 + 拖动）。设计书禁止的全部背包操作（丢弃/移动/拆分/合并/数字键等）因**不使用 `AbstractContainerMenu`** 而天然不存在。
  - 权衡说明：也可走自定义 `MenuType`（文档 `docs/inventories/menus.md`）换取原版槽位同步协议，但需要逆向压制大量原版行为（quickMove、数字键、拖拽），与设计书的"只读映射"语义冲突，**推荐自定义载荷 + 自定义 Screen**。
- **PVP 拾取界面**：双栏只读布局，同一套 Screen/载荷体系。服务端校验事务版本 + 条目状态后，向所有正在查看该事务的玩家广播状态更新（界面同步移除）。
- **倒下交互目标**：注册自定义实体（`DeferredRegister<EntityType<?>>`，标准流程）。死亡玩家的 `ServerPlayer` 实体在重生前虽仍被追踪，但客户端不再渲染躯体，因此可交互的"倒下玩家"应使用自定义标记实体（可渲染为倒地玩家模型），死亡位置生成、结算时移除。右击经 `PlayerInteractEvent.EntityInteractSpecific`（已确认存在）拦截并打开界面。
  - 注意：实体随区块卸载；事务数据在 SavedData 中权威存在，实体缺失时拾取交互暂不可用（区块重新加载后恢复），不破坏一致性。
- **PVP 抛物**：物品从死亡位置生成 `ItemEntity`，初速度指向操作玩家（`setDeltaMovement`），`setPickUpDelay(40)` 与原版丢弃一致；`Player.drop` 源码（`Player.java:732`）已核对参数，可完全复刻其抛掷语义。

### 4.4 重生返还

- `PlayerEvent.PlayerRespawnEvent`（已确认存在）中按设计书顺序返还：原槽位为空 → 原槽位；否则 `Inventory#placeItemBackInInventory`（安全插入，Soulbound 源码同款）；仍失败 → 玩家脚下 `player.drop`。经验经 `giveExperiencePoints(Xe)` 返还。
- 需要额外兜底：`PlayerEvent.Clone`（isWasDeath）时把未返还的保留物品从 oldPlayer 侧转移（防止返还逻辑与重生顺序竞争）。
- 玩家掉线（非服务器关闭）：`PlayerLoggedOutEvent` 中结算为"放弃选择"（n=0、物品照原版掉落、经验按 D(X₀) 生成经验球）。需区分服务器正常关闭（`server.isStopped()` 阶段触发的登出不算放弃），事务留给 SavedData 恢复。
- 玩家死亡期间重连：登录后若存在进行中事务，服务端重发预备载荷与当前状态，客户端重新弹出选择界面（同 §4.3 的替换点，不依赖原版是否重发 combat kill 包）。

## 五、与参考模组的兼容性（源码级证据）

| 模组 | 接管机制（源码核实） | 与 MVE 的共存结论 |
| --- | --- | --- |
| **GraveStone**（maxhenkel, Neo） | corelib `PlayerDeathEvent`（NORMAL 优先级）→ 物品存入墓碑方块实体，`event.removeDrops()` 清空掉落集合；自身检查 keepInventory | 其监听在 MVE（LOWEST）之前执行：墓碑拿走全部 ⇒ MVE 看到空集合 ⇒ **静默退出**（符合设计书）。部分拿走 ⇒ MVE 只接管剩余 |
| **inventory-protection**（Neo） | `LivingDropsEvent`（NORMAL）`getDrops().removeAll(...)` 摘走受保护物品存入 `PERSISTED_NBT`；`LivingExperienceDropEvent` 取消；`PlayerRespawnEvent` 返还 | 与 MVE 同事件不同优先级，NORMAL 先于 LOWEST ⇒ **无冲突**；其方法本身就是 MVE 方案的可行性佐证 |
| **Soulbound**（imoonday, Neo） | `InventoryMixin` 在 `dropAll` HEAD/RETURN 预留/放回灵魂绑定物品 ⇒ 这些物品**从不进入掉落集合**；`PlayerEvent.Clone` 在重生时复制；Curios `DropRulesEvent` 联动 | 灵魂绑定物品根本不出现在 `LivingDropsEvent` ⇒ MVE 看不到、不接管，**天然无冲突**（符合"已被其他机制接管的物品不重新处理"） |
| **PlayerRevive**（team.creative, Neo） | 玩家先进入"流血"状态避免死亡；真正死亡前触发 `PlayerBleedOutEvent` | MVE 挂点在真实死亡结算内，流血/复活阶段完全不感知 ⇒ **仅在最终死亡后介入**（符合设计书） |
| **Curios**（C4, Neo） | 饰品死亡掉落在 `LivingDropsEvent` 内部处理，公开 `CurioDropsEvent`（可取消、携带 drops 集合）与 `DropRulesEvent` | 饰品物品会出现在 drops 集合中，但其"槽位号"不属于原版 Inventory ⇒ MVE 需要显式支持：挂点①同时快照 Curios 槽位（`CuriosApi`），身份映射覆盖饰品格；或消费 `DropRulesEvent`。**工作量项，无阻塞** |

补充说明：NeoForge 1.21.1 中不存在 `PlayerDropsEvent`，因此"参考模组用 PlayerDropsEvent 抢东西"的旧式冲突源在 1.21.1 生态中基本消失，各家（GraveStone/inventory-protection/Curios）统一汇聚在 `LivingDropsEvent`，优先级即可裁决。

## 六、设计书需要修正/决策的差异点

### 6.1 `PlayerDropsEvent` 不存在（必改）

设计书若在任何实现笔记中引用该事件，改为 `LivingDropsEvent` + 身份匹配摘除方案（§三）。

### 6.2 槽位 ID 表与 1.21.1 不符（必改）

`Inventory.java:25-38` 实际常量：`INVENTORY_SIZE=36`、`SLOT_OFFHAND=40`；结构为 `items[0..35]`（0–8 快捷栏、9–35 主背包）+ `armor[0..3]`（靴→盔）+ `offhand[0]`。设计书中"主手 98 / 副手 99 / 盔甲 100–103"是其他映射体系的值。建议改为：

| 区域 | MVE 内部槽位 ID（建议） | 说明 |
| --- | --- | --- |
| 快捷栏 | 0–8 | `items[0..8]` |
| 主物品栏 | 9–35 | `items[9..35]` |
| 盔甲 | 36–39 | `armor[0..3]`，靴→盔 |
| 副手 | 40 | `SLOT_OFFHAND` |
| 主手 | 不单独渲染 | `items[selected]` 动态引用，与设计书"避免重复显示"一致 |

设计书已注明"以开发时实际值为准"，此处仅落实具体值。

### 6.3 消失诅咒"禁用状态"的展示（需决策）

原版在 `destroyVanishingCursedItems()` 中于掉落前销毁此类物品 ⇒ MVE 在 `LivingDropsEvent` 看不到它们，UI 上无法自然出现"红色禁用格"。两个方案：

- **方案 A（推荐，零 Mixin）**：挂点①扫描背包，含消失诅咒的物品预摘除为"禁用"条目（不参与掉落）；结算时按原版语义销毁（或按配置掉落）。净效果与原版一致（物品消失），但满足设计书的 UI 展示与"PVP 不可取得"。
- **方案 B**：接受其直接消失，不进入 UI；设计书相应措辞改为"消失诅咒物品按原版规则销毁"。

### 6.4 界面打开时序（实现注意）

combat kill 包在 `ServerPlayer.die` 内、挂点①之后发出 ⇒ MVE"预备"载荷必须在挂点①发送（同队列顺序保证）。若挂点②发现无可接管物品，服务端补发回退载荷让客户端切回原版死亡屏。已在 §4.3 给出完整流程。

### 6.5 其他实现注意项

- 死亡玩家是否还能拾取地面物品需在实现时用测试确认（预期不能，`ItemEntity` 拾取要求存活）；即使能，玩家背包已被清空、结算由服务端权威处理，不构成一致性风险。
- 同优先级（LOWEST）的其他模组监听器存在注册顺序不确定性 ⇒ MVE 必须坚持"只摘除身份匹配条目、绝不取消事件"，未匹配条目留在集合内正常生成，冲突自动退化为安全行为。
- `LivingDropsEvent` 在 `dropFromLootTable` 之后触发：玩家本体无战利品表掉落，但个别模组可能借该途径塞入额外物品——未匹配身份的条目不会被 MVE 接管。
- 经验条 A/B 与计时器均为客户端实时反馈，最终结算以服务端事务版本号为准（设计书已声明，载荷协议中带版本即可）。

## 八、结论与建议的模块划分

**可行性判定：通过。** 所有核心机制（死亡接管、物品冻结、经验曲线、双界面、PVP 竞争、持久化、断线放弃、兼容退化）均有已核对的 API 支撑，剩余工作量为常规实现，无需任何服务端 Mixin（仅 1 个客户端 Mixin）。

建议包结构（对应 `io.github.devxieyc.millionvalueexfil`）：

```text
transaction/   死亡事务：候选/提交/结算/幂等/持久化(SavedData)
event/         挂点①②③ + Respawn/LoggedOut/ServerTick
xp/            C(n)、n_max、E(L) 反查、D(Xr)、配置曲线
net/           载荷定义与编解码（预备/状态/操作/回退/PVP 更新）
entity/        倒下交互目标实体
compat/        Curios 显式槽位支持等（ModList 探测）
client/        MVEDeathScreen、PVP 拾取 Screen、滚动组件、Mixin 入口
config/        触发条件、伤害类型名单、曲线参数、k/t 等
```

推荐实现顺序：①事务核心 + 挂点链路（纯服务端、可用 /kill 与 keepInventory 直接验证）→ ②网络与倒下玩家界面 → ③PVP 目标实体与拾取界面 → ④崩溃恢复与幂等测试 → ⑤Curios 兼容。
