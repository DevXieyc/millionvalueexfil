# 研究：不掉落类模组（灵魂绑定/不掉落图腾/饰品保留）与 MVE、墓碑的共存

> 证据：Soulbound-neoforge-1.21.1 / inventory-protection-1.21.1-neo / Curios-1.21.1 源码（refer/）。
> 回答：这类"物品自保留"模组与 MVE 托管、墓碑收集能否同时兼容？——能，且大部分已是结构性兼容，
> MVE 无需为其中任何一个写适配代码。

## 一、三类"不掉落"模组的挂点（源码核实）

### 1. Soulbound（灵魂绑定附魔）
- **原版物品栏**：`InventoryMixin` 注入 `Inventory.dropAll` 两端——HEAD 时把有灵魂绑定附魔的物品
  **预留下架**（槽位临时置空，`dropAll` 扫不到），RETURN 时原位放回。净效果：灵魂绑定物品
  **从未进入掉落集合**，且在旧玩家实体物品栏中存活到重生。
- 重生返还：`PlayerEvent.Clone`（wasDeath）扫描旧实体物品栏 → 按槽位/回落方式放进新玩家
  （可按配置随机损耗耐久）。
- **饰品栏**（装了 Curios 时）：注册 Curios `DropRulesEvent` 覆写 → `ALWAYS_KEEP`。

### 2. Curios（饰品栏框架，保留逻辑的承载体）
- `LivingDropsEvent` **@HIGHEST**（CuriosEventHandler.playerDrops）：遍历饰品槽，
  按掉落规则（含 Soulbound 的覆写谓词）决定保留/丢弃——**保留的物品根本不入池**
  （留在饰品栏，Clone 时由 Curios 整体拷贝到新实体），丢弃的才并入集合（`drops.addAll(curioDrops)`）。

### 3. inventory-protection（"不掉落图腾"= Protector 物品）
- `LivingDropsEvent` **@NORMAL**（默认优先级）：若掉落集合中出现 Protector，则
  `event.getDrops().removeAll(...)` **整体回收全部物品**，序列化进 `PERSISTED_NBT`
  （键 `InventoryProtection_playerInventoryDrops`），并取消经验掉落（`LivingExperienceDropEvent`）。
- `PlayerRespawnEvent`：按护甲槽/物品栏还原全部物品 + 返还经验。

## 二、与 MVE 的交互：命运判定即让位机制

MVE 在 `LivingDropsEvent` 托管时做 fate diff：**死亡快照中存在、但掉落集合中缺席的物品 = DISABLED**
（与消失诅咒同等待遇：不可选择、结算时移除）。三类模组的保留物恰好全部"缺席"：

| 模组 | 保留物去向 | MVE 看到的集合 | MVE 行为 |
|---|---|---|---|
| Soulbound（原版栏位） | dropAll HEAD 预留，未入池 | 缺席 | fate=DISABLED，自动让位 ✓ |
| Curios ALWAYays_KEEP（饰品栏） | HIGHEST 拦截，未入池 | 缺席 | fate=DISABLED，自动让位 ✓ |
| inventory-protection | NORMAL 清空集合 | 空 | matched=0 → **整体中止**（经验原版球 + ClosePayload），静默退出 ✓ |

结论：**不需要任何 per-mod 适配**。Soulbound 物品在 MVE 选择界面里显示为灰格（语义正确："此物自有归属"）；
inventory-protection 存在时 MVE 完全退出（日志可见 "commit aborted"）。双方各自的 PERSISTED_NBT 键
互不冲突（MVE 交易键 / inventory-protection 的回收键）。

## 三、与墓碑的共存：管线位置组合

```text
dropAll HEAD          Soulbound 预留（物品不入池）
LivingDropsEvent
  @HIGHEST  Curios    饰品保留（不入池）
  @NORMAL   inventory-protection  整体回收（集合清空 → MVE 中止）
  @LOW      MVE       fate diff → 托管（缺席者自动让位）
  @LOWEST   corelib   墓碑收集（processDrops + removeDrops）
  事件结束             剩余 addFreshEntity（= 真正的"掉落"）
```

- **不入池的物品**（灵魂绑定/饰品/被回收者）：既不会进 MVE 托管，也不会进墓碑——
  由各自的模组在重生时还原 ✓ 不存在"墓碑和原模组双重返还"。
- **入池的物品**：MVE 托管 → 结算重放（IS13）→ corelib 墓碑收下未保留部分 ✓。
- 两类兼容同时成立的唯一工程约束：**MVE 的托管优先级必须在 NORMAL 之后、LOWEST 之前**
  （IS15 的 LOW 定位）——绝不能提到 HIGHEST，否则会抢在 Curios/Soulbound/inventory-protection
  之前把它们的保留物卷进托管。这把 IS15 从"建议"升级为"硬约束"。

## 四、套装效果类模组（不做掉落保护的那种）

套装物品若没有保留机制，就是普通的入池物品 → 正常进 MVE 托管。玩家花经验保留其中一件导致套装
效果失效，属于物品级保留语义下的正常博弈结果（设计书的经验费用模型正好刻画"保留的代价"），
不是兼容问题。真正要避开的是"套装破碎时主动清除/丢弃其余部件"的激进模组——但那时物品已在
MVE 的交易 NBT 里而非掉落集合中，此类模组无从触达；只需在文档中声明：MVE 托管期内物品
免疫一切掉落期副作用，选择窗口结束后按标准管线释放。

## 五、备忘

- Soulbound 的 Clone 返还发生在重生瞬间，与 MVE 的 onRespawn 返还同刻但物品集合互斥
  （灵魂绑定物不在 MVE 交易中），无槽位冲突。
- inventory-protection 的经验返还用 `totalExperience` 整值；MVE 冻结经验为 0 → 无叠加。
- 若未来引入更多"事件后保留"型模组（LOWEST 之后再清集合），需单独评估——那会与墓碑竞态。
