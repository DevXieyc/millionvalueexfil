# 研究报告：互助 → 真死 → MVE 托管 → 墓碑 三方管线

> 代号：IS14-IS17（OPEN，仅调查未编码）
> 证据来源：PlayerRevive 1.21 源码（refer/PlayerRevive-1.21.zip，ReviveEventServer/ReviveEventClient/
> PlayerReviveServer/Bleeding）、corelib 2.1.4 源码（GitHub 1.21.1 分支）、NeoForge 21.1.250 反编译源码。
> 设计原则（用户定调）：MVE 是火中取栗——尽量复用原版事件而非自行实现平行逻辑，在标准管线上占据正确的
> 位置来兼容生态，绝不为适配某个模组走独立小路。

## 一、场景

服务器管理员同时装：互助类模组（PlayerRevive）+ MVE + 墓碑（GraveStone）。理想状态：
1. 玩家致命伤 → 进入倒地/互助状态（可被队友救助）；
2. 无人救助 → 流血结束 → **真死**；
3. 真死 → MVE 物品选择窗口；
4. 未被带走的物品 → 原地生成墓碑。

## 二、PlayerRevive 源码核实（机制）

- 首次死亡：`LivingDeathEvent` @HIGHEST（无 receiveCanceled）→ `startBleeding` + `event.setCanceled(true)`
  + 设置 `bleedingHealth`。事件被取消 → 无战斗终结包 → 原版死亡屏不出现，进入倒地状态。
  倒地期间**不碰物品栏与经验**（只改饥饿/效果/姿势），玩家实体一直活着。
- 救助成功：`PlayerReviveServer.revive()` 恢复健康 → 从未真死 → MVE 全程无感（唯一痕迹：一次被取消的
  快照回滚）。
- 真死路径：倒地计时结束 → `kill()`：`setHealth(0)` → **`player.die(BLED_TO_DEATH)`** —— 走完整原版
  die() 管线。PR 自身对 `BLED_TO_DEATH` 来源放行（`doesByPass`），事件不被取消。
  关键确认：`kill()` 末尾的 `revive.revive(player)`（"compatibility reason" 兜底）只清 bleeding 状态
  字段，**不碰 health** → 真死实体保持 health=0 → MVE 所有 `isDeadOrDying` 门闸有效。
  兜底语义反过来也成立：MVE 从不取消 LivingDeathEvent → PR 的"没死成"兜底不会被 MVE 误触发。
- 登出即死：`PlayerLoggedOutEvent` @HIGHEST → 倒地中登出强制 `kill()` → 在登出事件栈内真死。
- 客户端 GUI 锁定：`ScreenEvent.Opening` 处理器，`disableAllGUIAccess=true` 时取消除 `DeathScreen`
  及 PauseScreen 外的一切屏幕打开（该配置默认 false；`bleedInSingleplayer` 默认 false，单机不激活）。
- 倒地中的右键：`EntityInteract` @HIGH 仅在目标 bleeding 时拦截转救助流程；真死后标记已清，
  不影响 MVE 的 PVP 拾取。

## 三、三方时间线（理想管线，全部落在标准事件语义上）

```text
致命伤
├─ LivingDeathEvent
│   ├─ MVE @HIGHEST：快照 + 冻结XP（prepare 暂不发，见修正点1）
│   ├─ PlayerRevive @HIGHEST：非绕过来源 → 倒地 + 取消事件
│   └─ MVE @LOWEST+receiveCanceled：已取消 → 回滚快照、解冻XP
│       （HIGHEST 同级注册序两种先后都安全；corelib @LOWEST 收不到被取消的事件，
│        不建死亡快照、无污染 ✓）
├─ 倒地：MVE 零痕迹；救助成功 → 结束（MVE 无感）
├─ 无人救助 → kill() → player.die(BLED_TO_DEATH)
│   ├─ LivingDeathEvent（未取消）
│   │   ├─ MVE @HIGHEST：快照 + 冻结XP
│   │   └─ corelib @LOWEST：deathMap 快照（XP=0✓ 物品栏完整✓ 位置=死亡点✓）
│   ├─ LivingDropsEvent
│   │   ├─ NORMAL：Curios/Soulbound/inventory-protection 调整集合
│   │   ├─ MVE @LOW（修正点2）：fate diff → 托管 → 取消事件
│   │   └─ corelib @LOWEST：已取消 → 跳过 → 死亡时刻无墓碑、无空墓 ✓
│   │       （deathMap 条目保留，成为重放时的墓碑数据源——闭环）
│   ├─ MVE 选择窗口（玩家实体仍躺在死亡点，右键=PVP 拾取）
│   └─ 超时/放弃/登出结算：保留XP→owner，损失XP→orbs，
│       未保留物品 → CommonHooks.onLivingDrops(owner, BLED_TO_DEATH, drops, false) 重放
│       ├─ corelib @LOWEST：deathMap.remove 命中原快照 → processDrops(未保留物品)
│       │   → PlayerDeathEvent → GraveStone 建墓（位置=死亡点，槽位=原位，XP=0）✓
│       └─ 无人接管 → MVE 原地生成掉落（现状即兜底）✓
└─ 点重生 → PlayerRespawnEvent → MVE 返还保留物品
    （修正点4：此路径重放需用旧实体派发，见风险）
```

与上一轮结论的差异：**登出放弃路径的重放由"不可行"修正为"技术上可行、需实测"**——PR 的 logout-kill
发生在 `PlayerLoggedOutEvent` 栈内，该栈内实体仍有效、位置=死亡点，MVE 的 onLogout（默认 NORMAL，
晚于 PR 的 HIGHEST）此时重放掉落事件即可让墓碑接管，替代当前的 dropAll 原地爆出。

## 四、需要修正的点（零 per-mod hook，全是管线语义）

| # | 修正 | 性质 |
|---|------|------|
| 1 | PreparePayload 从 HIGHEST 处理器移到"确认未取消"分支（LOWEST 回滚分支的反面）。同栈内微秒级延迟，客户端时序不变；消除对一切"取消死亡"模组（互助/复活类）的占位屏污染（当前会盖住倒地 UI 5 秒） | 正确性修复（IS14） |
| 2 | drops 托管优先级 LOWEST→LOW：位于 NORMAL 调整者之后（fate diff 仍准确）、LOWEST 墓碑之前（MVE 必定先于 corelib，消除同级注册序竞态）；全托管时取消事件：压制空墓、压制低位消费者 | 管线定位（IS15，并入 IS13 实施） |
| 3 | abandon（登出）结算路径接入重放（同上：PlayerLoggedOutEvent 栈内实体有效） | IS13 修正 |
| 4 | MveDeathScreen / MvePendingScreen extends 原版 DeathScreen：MVE 的死亡界面在类型上**就是**死亡屏——GUI 锁定类模组的放行名单（`instanceof DeathScreen`）自然放行，fallback 代码里手动 new DeathScreen 的分支也可统一。已验证：public 构造器 `(Component,boolean)`、非 final、覆写 init/render 即可，isPauseScreen=false 语义自动继承 | 类型语义声明（IS16） |
| 5 | DeathTx 补记死亡来源（存 DamageType 的 ResourceKey，NBT 友好）供重放用；给断线玩家发包前加连接检查（PR logout-kill 场景） | 实施细节（IS17） |

## 五、待实测风险

1. respawn 结算路径的重放：旧实体已 discard，作为事件源派发的可用性需实测；corelib 会命中 deathMap
   残留快照（墓碑位置仍正确）。失败回退：直接掉落 + corelib deathMap 每 respawn 路径死亡泄漏一条
   （per-player，重启清零，低危）。
2. 重放的 GraveStone 副作用与 IS13 清单相同：讣告/死亡记录翻倍、墓碑定位失败兜底（已确认失败时
   removeDrops 不会被调 → 集合剩余 → MVE 兜底掉落 ✓）。
3. PR `disableAllGUIAccess=true`（非默认）时：修正点4 落地后 MVE 两屏均被放行 ✓；
   MvePendingScreen extends DeathScreen 后同样适用。
4. PR 与 MVE 在 HIGHEST 的注册序：修正点1 落地后两种序均安全（现状 MVE 先注册时会提前发 Prepare）。
5. Corail Tombstone / 其他互助模组（如 moreprone 类）未验证，但契约相同：LivingDeathEvent 取消 +
   LivingDropsEvent 集合语义。

## 六、结论

管理员理想管线在纯标准事件语义上**可达**：MVE 占据 HIGHEST（先手快照）/ LOW（托管+取消）/
结算重放（CommonHooks.onLivingDrops）三个标准位置，PR 与 GraveStone 各自在自己原本的位置上工作，
三方无需任何一方认识另一方。实施顺序建议：修正点1、4（小，正确性）→ 修正点2、5 → 修正点3（需实测）。
