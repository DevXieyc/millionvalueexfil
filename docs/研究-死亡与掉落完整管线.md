# 研究：完整死亡与掉落管线（1.21.1 源码逐行核实版）

> 证据：NeoForge 21.1.250 反编译源码（LivingEntity / Player / ServerPlayer）+ corelib 2.1.4 +
> PlayerRevive 1.21 源码 + MVE 实测日志。本文回答两个问题：
> ① 互助是否给玩家"加了一个状态"，图腾在什么节点起作用；② 墓碑是否处于"掉落前→收集→掉落后"。
> 行号以 neoforge-21.1.250-sources.jar 为准。

## 〇、总览

```text
阶段0 伤害结算 ──→ 阶段1 濒死瞬间[图腾关卡] ──→ 阶段2 死亡宣告[LivingDeathEvent] ──→ 阶段3 掉落[LivingDropsEvent]
                                                                                    ──→ 阶段4 死后状态 ──→ 重生
```

原版没有"濒死"状态：health≤0 的结算点与死亡宣告发生在**同一 tick 的同一调用栈内**。
玩家可干预的关卡只有两道：宣告前的图腾回滚、宣告时的 LivingDeathEvent 取消。

## 一、阶段0：伤害结算（LivingEntity.hurt）

1. `LivingIncomingDamageEvent`（可取消——伤害尚未发生；PlayerRevive 的倒地保护在此拦截二次伤害）；
2. 盾牌格挡（`LivingShieldBlockEvent`）→ 盔甲/附魔/吸收减伤 → `LivingDamageEvent.Pre`（可修改最终伤害；
   PlayerRevive 的 overkill 追踪挂在此 @LOWEST）→ 伤害真正入账（health 扣减）→ `LivingDamageEvent.Post`。

## 二、阶段1：濒死瞬间与不死图腾（第一关卡）

hurt() 尾部（LivingEntity.java:1260）：

```java
if (this.isDeadOrDying()) {                              // 伤害结算后 health≤0
    if (!this.checkTotemDeathProtection(source)) {       // ← 图腾关卡
        this.die(source);                                // 通过关卡才会宣告死亡
    }
}
```

`checkTotemDeathProtection`（:1306）：遍历主/副手找不死图腾 → NeoForge `onLivingUseTotem`（可被模组拦截）→
成功则**消耗图腾、setHealth(1.0F)、移除可净化效果、附加回环/伤害吸收**。
关键结论：**图腾关卡位于"伤害已致死、死亡未宣告"之间**——救活时 `die()` 根本不会被调用，
LivingDeathEvent 不派发、不掉落、无死亡屏。原版只有"濒死瞬间"，没有"濒死状态"。
`BYPASSES_INVULNERABILITY` 类伤害（/kill 等）无视图腾。

## 三、阶段2：真实死亡宣告（ServerPlayer.die:685）

服务端玩家死亡**只走 `ServerPlayer.die` 一个入口**（完整覆写，不调 Player.die / LivingEntity.die；
后两者的同款事件钩子分别只服务客户端侧与非玩家实体——日志证实每次死亡事件仅派发一次）：

```java
gameEvent(ENTITY_DIE);
if (CommonHooks.onLivingDeath(this, cause)) return;      // ★ LivingDeathEvent，唯一一次
    ↓ 未取消
connection.send(ClientboundPlayerCombatKillPacket)       // ★ 客户端死亡屏触发点（早于掉落！）
    + 死亡消息广播（队伍可见性规则）
removeEntitiesOnShoulder(); 宽恕中立生物;
dropAllDeathLoot(serverLevel, cause);                    // ★ 进入阶段3（非旁观者）
计分板 DEATH_COUNT / 统计 / 凋零玫瑰 / byte3 死亡动画 / 记录 lastDeathLocation
```

"真实死亡"的宣告点 = LivingDeathEvent 派发完毕且未被取消。被取消（互助类模组）则 die() 提前返回，
玩家 health 仍为 0？——不：取消者负责回滚（PlayerRevive 随后 setHealth(bleedingHealth)），
否则客户端会停留在 health=0 的活体状态。

## 四、阶段3：掉落管线（LivingEntity.dropAllDeathLoot:1462）

```java
captureDrops(new ArrayList<>())                          // NeoForge 收集补丁：此后所有 drop() 入池
[仅生物：shouldDropLoot && doMobLoot → 战利品表 + dropCustomDeathLoot]   // 玩家不走这段
dropEquipment()
  └─ Player.dropEquipment:  keepInventory=false 时
       destroyVanishingCursedItems()                     // 消失诅咒（数据驱动 PREVENT_EQUIPMENT_DROP）
       inventory.dropAll()                               // ★ 全部物品入池
dropExperience()                                         // ★ 经验球在这里生成——早于物品掉落事件！
  └─ 玩家: isAlwaysExperienceDropper()=true（无视 doMobLoot/lastHurtByPlayer）
     数量 = min(experienceLevel*7, 100)（getBaseExperienceReward:1841）；
     keepInventory=true 或旁观者 → 0；NeoForge LivingExperienceDropEvent 可改
drops = captureDrops(null)                               // 收口：得到完整物品集合
if (!CommonHooks.onLivingDrops(...))                     // ★ LivingDropsEvent——唯一统一的物品接管窗口
    drops.forEach(addFreshEntity)                        // "物品掉落完成"= 这里
```

LivingDropsEvent 派发内的优先级槽位（HIGHEST→LOWEST，同级按注册序）：

| 槽位 | 消费者 | 行为 |
|---|---|---|
| NORMAL | Curios / inventory-protection / Soulbound | 保留/回收/调整集合 |
| MVE | 托管 | fate diff → 托管进选择流程（详见三方管线报告） |
| LOWEST | corelib/GraveStone | processDrops（死亡快照按 ItemStack.equals 匹配槽位）→ PlayerDeathEvent → 填墓碑 → removeDrops 清空集合 |

## 五、阶段4：死后状态与重生

- 玩家实体**不消失**：isDeadOrDying 躺在原地（Pose.DYING），不走生物的 tickDeath 移除，等待重生。
- 客户端在 CombatKill 包到达时进死亡屏——**早于服务端掉落完成**（MVE 能在掉落窗口内抢发 Prepare 的原因）。
- 客户点"重生" → PlayerList.respawn：新建 ServerPlayer、`PlayerEvent.Clone`（PERSISTED_NBT 在此拷贝）、
  `PlayerRespawnEvent`。旧实体移除。

## 六、对两个问题的直接回答

### Q1：互助是给玩家加了一个状态吗？图腾在什么节点作用？

**不是在原版状态机上插入状态，而是旁路自建状态机。** 原版死亡是两态的：
"濒死瞬间"（无状态，同 tick 走完宣告+掉落）与"已死未重生"（health≤0 躺尸等重生）。
PlayerRevive 的"濒死"实现为三步：
1. `LivingDeathEvent` @HIGHEST **取消死亡宣告**（die() 提前 return，不掉落、不发终结包、无死亡屏）；
2. 玩家保持存活（setHealth(bleedingHealth)），挂自定义 capability（IBleeding：倒计时/救助进度/伤害源克隆），
   由 PlayerTickEvent 驱动——这个"濒死状态"完全是模组私有物，原版管线全程无感知；
3. 到期（或倒地登出）`kill()`：setHealth(0) → `die(BLED_TO_DEATH)` **重新走一遍完整原版死亡管线**
   （BLED_TO_DEATH 在其自身过滤器里放行，二次进入不被取消）。

图腾关卡在互助关卡**之前**（hurt 尾部 vs die 内部）：图腾救活 → LivingDeathEvent 根本不派发 → 互助无从介入。
两者天然兼容、顺序固定：图腾 →（失败才）宣告死亡 → 互助取消。

### Q2：墓碑是"掉落前→墓碑收集→掉落后"吗？

**模型正确，需精确定位一处**：墓碑收集不是掉落前后之间的独立第三阶段，而是
`LivingDropsEvent` 派发内部 **LOWEST 槽位**上的消费者（掉落前窗口的最后一位）。它通过
`removeDrops`（清空集合）把"物品掉落后"短路掉——集合空了，`addFreshEntity` 落空，物品以墓碑形态存在。
另注意：**经验球在物品掉落事件之前就已生成**（dropExperience 在 captureDrops 收口之前），
墓碑存的经验取自 LivingDeathEvent @LOWEST 时的死亡快照（corelib deathMap），两者天然一致。
MVE 冻结经验在事件 HIGHEST，因此快照与原版经验球都是 0，无双返还（与实测日志吻合）。

## 七、附：玩家死亡完整时序（单 tick 内，除非模组取消/托管）

```text
hurt(): IncomingDamage → 盾/甲/吸收 → DamageEvent.Pre → health 扣减 → DamageEvent.Post
  → health≤0 → [图腾?] → die() → [LivingDeathEvent（MVE快照/PR取消/corelib快照）]
  → CombatKill 包（客户端进死亡屏）→ dropAllDeathLoot:
      captureDrops 开始 → inventory.dropAll → 消失诅咒销毁 → XP 球生成
      → [LivingDropsEvent（调整者→MVE托管→corelib墓碑→removeDrops）]
      → 剩余 addFreshEntity（物品掉落完成）
  → 统计/动画/记录死亡位置
（之后任意 tick）玩家点重生 → Clone + Respawn
```
